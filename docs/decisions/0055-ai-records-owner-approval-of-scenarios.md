# ADR-055 The AI records the owner's approval of scenarios; amends ADR-010 and ADR-023 (2026-10-17, owner decision, agent consensus on mechanism)

Context: ADR-010/023 made the human the oracle for intent by letting only the human set `approved` and run `lm accept --bless` from an interactive terminal. In practice (Roadster Lander, ADR-054) the owner had to learn the file format and two commands, and a first `--bless` locked nothing because no status had been flipped. Owner decision (after trying the old flow a couple of times): the AI using the language walks the owner through proposed scenarios in conversation; the owner approves, rejects or asks for changes; once the owner explicitly gives the blessing, the AI writes the approvals and the lock. The owner stays the oracle; the AI does the typing.

Options for the mechanism: (a) a non-TTY `--bless` plus a status edit by the agent (global re-bless can absorb unrelated changes); (b) `--approve` by name with a `--by` quote (agy); (c) a digest-bound transaction with JSON review manifests and separate evidence records (Codex); (d) as (b), but scenarios are named by the digest shown in the review, so the approval binds to the exact reviewed text (Claude, merging b and c).

Decision (d):
1. `lm accept --review` shows each scenario's digest. `lm accept --approve DIGEST.. --by "TEXT"` sets those scenarios to `approved` and locks exactly them; it refuses if a digest does not match a current scenario (changed after review), if `--by` is empty, or if nothing is named. It works without a TTY. No other scenario or lock entry is touched.
2. Evidence: the lock line for each approved scenario keeps `<digest> <name>` and appends the date and the owner's exact words; the commit that records it carries an `Approved-by-owner: "<words>"` trailer. `--guard` is unchanged in what it fails on and tolerates lines with or without the evidence suffix.
3. Protocol (AGENTS.md rule 5, docs/TESTING.md): per scenario the AI shows name, why, what is run in plain words, the expected result, what the program does today, and for a modification the before/after. The owner may ask questions about any scenario; the AI answers in domain terms (using `lm explain` or `lm run` to show real behavior, never guessing) before asking again. It asks for an explicit answer. Clear assent ("approved", "yes", "bless them", an emoji the owner has declared as a blessing, ✅ by default) counts; anything ambiguous is asked again; partial answers approve only what was named. A modified scenario returns to `proposed` and needs a new approval. The AI never approves on its own judgment, never on another agent's word, and never to make a failing guard pass.
4. The interactive `--bless` path stays for humans who prefer it.

Who agreed: agy and Codex on keeping the TTY path, recording the owner's words, modified scenarios returning to proposed, and that an agent-written quote is auditable but cannot prove authorization. Codex on binding approval to digests and scoping it (adopted via digest arguments); agy on lock-line metadata and the commit trailer (adopted). Codex's separate JSON evidence records not adopted: too much ceremony for a single-owner prototype.

Risk accepted: the hard TTY barrier becomes an audited convention; a fabricated approval is detectable only by comparing the lock/commit quote with the conversation.

Amendment 2026-10-18 (owner choice, "Add --retire (Recommended)"): renaming or deleting an approved scenario left a MISSING lock line that only `--bless` could clear. `lm accept --retire NAME.. --by "TEXT"` drops exactly those lines, refusing names that are not locked or whose scenario still exists; the owner's words go in the commit trailer, since the lock line itself is removed.
