# ADR-050 M11 implemented: choices ADR-049 left open (2026-10-17)

Implements ADR-049 items 1-7 in every layer (types, reader-level reserved words, checker, interpreter, stdlib `map`/`set`, Python prims and Go twins, lowering, Go runtime, SPEC); no item changed. Decided by Claude under ADR-030's delegation.
1. Naming (ADR-047): `get` is a reserved word, so ADR-049's `map.get` is `map.at (m key) -> (Opt v)`, the same name and shape as `list.at`. Parameters are named `key`/`value`/`default` (`keys`/`values` are functions of the module).
2. Key constraint. A type expression `(Map K V)`/`(Set K)` whose `K` is concrete and not Int, Float, Str or Bool is E-TYPE at once (signatures, lambda parameters, record fields, aliases). A type variable may be a key in a signature; it then acts as a constrained variable: every instantiation (a call or function reference, an example's own fn, `lm run` arguments) notes its key types and checks them once the fn's types are solved, exactly like ADR-043's operator constraints (an undetermined key, e.g. an unused `(mapof)`, defaults to Int). Inside a generic fn a rigid variable satisfies the constraint only if the fn's own signature uses it as a key, so `(sig (x a) -> Int)` cannot put `x` in a set (callers could pass a list). One diagnostic per offending type and fn, because every Map/Set-typed callee of one expression notes the same key.
3. Literals: keys/elements are Int, Float, Str literals or `true`/`false`; anything else is E-TYPE, a malformed `mapof` entry is E-PARSE, a duplicate (compared by value, so `1.0` and `1.00` collide) is E-DUP-NAME. `lm fmt` does not sort `mapof`/`setof` entries: `mapof` values are evaluated in written order, so reordering would change effects and which failure wins; printed values are in key order.
4. Representation: a persistent AVL tree, node = (key, value, left, right, height, size), so `size` is O(1). Rebalancing, insertion (replace on equal key), deletion (successor = minimum of the right subtree), and the set operations are the same steps in `lm/tree.py` + `lm/coll_prims.py` and `lm/runtime/go/coll.go`: `remove` of an absent key returns the argument unchanged; `union(s, t)` inserts `t`'s elements into `s` in ascending order; `intersect`/`diff` insert the kept elements of `s` in ascending order into an empty tree. Sets store unit as every value. Equality compares kind, size, then the in-order bindings; Python hashes the binding tuple. `map.update` and `set.from-list` are LM bodies (over `put`/`at`/`opt.unwrap-or` and `list.fold`/`add`), the rest are prims.
5. IR gains `MapLit(keys, items)` and `SetLit(items)` (keys are `Lit`s, values are left-to-right expressions); Go emits `mapOf([]Value{..}, []Value{..})`/`setOf(..)`. Go keys compare with a type switch (`cmpKey`); Str uses Go's byte comparison, which is code point order for valid UTF-8.
6. Tests: `tests/unit/test_maps.py` (AVL invariants under 20,000 random puts/removes against a dict model; equality across insertion orders and deletion histories; printed values re-read as constants and printed identically; `lm run` key order and key-type rejection), `tests/spec/run/maps.lm` (insertion orders, rebalancing deletions, Str/Float/Int/Bool order, empty-literal inference, nested sets, `mapof` evaluation order with a failure, an overflow inside `map.fold`; also run compiled by the differential test), `tests/spec/build/bin-maps.lm` (100k scrambled keys, half removed; interpreter ~3 s, binary 0.12 s; output pinned from a Python reference), `tests/spec/check/map-*.lm`/`mapof-*.lm`, `tests/spec/fmt/maps`.
7. Item 6 (`examples/colsum.lm`): `add-to` is gone; `Summary.totals` is `(Map Str Int)` grouped with `map.update`; output is in key order and the purposes and examples say so. Numbers in EVIDENCE.md. The old binary on 50k distinct keys was worse than quadratic (10k rows: 392 s); the likely cause is `add-to`'s non-tail recursion as deep as the number of keys (Go stack growth and GC stack scans), not profiled.
Known: `lm/gobackend.py` is 411 lines, slightly over the ~400 guideline (it was 406 before M11).
