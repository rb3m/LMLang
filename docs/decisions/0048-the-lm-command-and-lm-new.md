# ADR-048 The `lm` command and `lm new` (2026-10-17)

Goal (owner): LM should feel like a tool, not a repo. `bin/lm` is a POSIX sh wrapper that follows symlinks back to its checkout and runs `python3 -m lm` with that checkout on PYTHONPATH (`LM_PYTHON` overrides the interpreter), so `ln -s <checkout>/bin/lm ~/.local/bin/lm` gives an `lm` command usable from any directory. A project is any directory with `src/` (and optionally `tests/accept`, `accept.lock`): the loader already resolves stdlib and the Go runtime relative to the package and project paths relative to the working directory, so no project file is needed. `lm new DIR` scaffolds such a project (module named after DIR, a starter `main` returning an exit status, one example, one *proposed* scenario, a `.gitignore` for the binary) that passes fmt, check, test and accept --guard immediately (tests/unit/test_command.py). `lm build` now also looks for Go in the usual install locations when it is not on PATH (`~/.local/go`, `/usr/local/go`, Homebrew); `LM_GO` pointing at a missing file still means "no Go". Why a shell wrapper and not a pip package: zero install machinery, works with the stock Python on macOS and the server, and stays stdlib-only (R-Q1). README.md is now written for the human owner.
