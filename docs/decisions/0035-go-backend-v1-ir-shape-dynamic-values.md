# ADR-035 Go backend v1: IR shape, dynamic values, failures as panics, bounded recursion (2026-10-16, M8(c))

Context: ADR-026 fixes the pipeline (checked `Program` -> shared IR -> Go source -> `go build`) but not the IR shape or the runtime representation. Decided by Claude (M8 Go agent) under ADR-030's delegation.
1. IR (`lm/ir.py`, built by `lm/lower.py`). An expression tree, not statements: names stay LM names (fn ids `mod.name`, constructor ids `mod.Name` or prelude `Some`, error ids as the interpreter spells them); each backend mangles and linearizes for itself, so a Python backend can print most nodes as Python expressions. Lowering resolves what the interpreter decides at run time: direct `Call` vs `Apply` of a function value vs `PrimOp` (prelude operator with a `Site`), `FnRef`/`PreludeRef` for functions used as values, `Lambda` with explicit sorted `captures`, `Match` as ordered arms of `Test`s (tag/int/str/bool on an argument path from the subject) plus binds, `Fail`/`Try` nodes, and `Contract`s (expr + site + code). Only functions reachable from the roots are lowered, so an unused stdlib prim never blocks a build.
2. Values. One dynamic representation, `Value = any`: Int `int64`, Bool `bool`, Str `string`, Unit `UnitT`, List `[]Value`, variants `*Variant{*Ctor, args}`, records `*Record{*RecType, fields}`, function values `*Closure` (arity-1/2 fast paths). Equality and printing are one function each in `value.go`, line-for-line twins of `values.py`. Why: correct first, with one runtime for generic code (no monomorphization) and no use of checker types. Cost: boxing allocates Ints outside 0-255 and every op type-asserts. Measured (bench task primes, `count-below 10000`): interpreter 25.0 s, binary 0.59 s (~42x); without `SetGCPercent(400)` the binary took 1.6 s, so GC dominated. Revisit: when a real experiment is CPU-bound and a profile shows boxing, assertions or GC above half the time, or compiled code is under 20x the interpreter on bench tasks; then emit typed Go for monomorphic functions from checker types, keeping `Value` at generic boundaries.
3. Failures and faults. `Fail` panics with `*Fail`; `Try` runs its body in a closure with a deferred `recover` that keeps only failures whose id a handler names and re-panics everything else, so faults (`*Fault`: overflow, contracts, recursion, exit range) are never caught. Zero cost on the success path except at `try` sites. Any other panic is a toolchain bug and Go exits 2 with a trace, matching the CLI's exit 2.
4. Recursion. A Go stack overflow is fatal and cannot be recovered, so each LM call increments a depth counter; above 1,000,000 nested calls the fault is E-RECURSION-LIMIT. `debug.SetMaxStack` is raised to 8 GB (address space; memory is used only as the stack grows; the runaway fixture peaks near 100 MB). The interpreter's limit is lower (Python frames), so a program recursing between the two depths succeeds compiled and faults interpreted; differential tests stay below the interpreter's limit and `tests/spec/build/deep.lm` (depth 300,000) is binary-only.
5. Overflow (ADR-029/030) uses checked helpers `add sub mul div` with a site index; the fault JSON carries operator, operands, bounds, node path and enclosing fn. Not yet: call frames and the `lm run` replay of ADR-030 item 5; align with the interpreter's format when M8(b) lands.
6. Evaluation order. When a later argument needs statements (an `if`, `match`, `let`, `try`...), earlier non-trivial arguments are spilled to temporaries, so effects and failures happen left to right (`tests/spec/build/order.lm`). `new` evaluates fields in written order and stores them in declaration order.
7. Prims. One Go function per prim in `lm/runtime/go/prims.go`, named `prim_` + the prim name with `.`/`-` -> `_`, one `Value` parameter per LM parameter. `lm build` names any reachable prim without a Go function; a unit test fails while `lm/prims.py` has a prim the Go runtime lacks.
Known divergence: prelude operators used as values are shared closures in Go but fresh objects in the interpreter, so `=` on them can differ; comparing function values has no meaning and is not tested.
