# ADR-029 `Overflow` is an unchecked runtime fault, not a prelude error (proposed 2026-10-16, amends ADR-026)

Context: ADR-026 Decision 3 says `Overflow` "behaves like `DivZero` (implicitly possible on arithmetic, not declared in `fails`)". The premise is wrong: `DivZero` is declared and checked. `/` and `mod` fail `DivZero` unless the divisor is a nonzero literal (lm/prelude.py `FAILING`, SPEC section 7), callers must list it (E-FAILS-UNDECLARED), and `/` cannot be passed as a value. Taken literally, ADR-026 leaves two bad readings. (a) Declared like `DivZero`: every function that adds would need `(fails Overflow)`, `+ - *` could no longer be function values (`(list.fold xs 0 +)` breaks, ADR-015), and when nearly everything can fail, `fails` stops telling the reader anything. (b) A catchable error that is never declared: breaks G3 ("absent `fails` = cannot fail") and the checker's escape analysis, because a `try` could then catch something that no signature mentions.
Decision: overflow is a runtime fault in the same category as E-RECURSION-LIMIT and contract violations, not an LM error value.
- `+ - *` and `/` of min-int by -1 whose result leaves the signed 64-bit range halt the program with the diagnostic E-OVERFLOW (operator, operands, node path, enclosing fn). `mod` cannot overflow (min-int `mod` -1 = 0). Stdlib prims that can overflow (`math.abs` of min-int) do the same.
- No `Overflow` name is added to the prelude: it cannot be written in `fails`, `fail`, or `catch`, and is not reserved. Arithmetic stays pure and total in the type system, so `+ - *` remain usable as function values and no signature changes.
- An integer literal outside the range (in source, examples, scenarios or `lm run` arguments) is a check-time E-OVERFLOW, so constant overflow never reaches runtime.
- `--no-contracts` does not disable overflow checks: they are semantics, not contracts. An example that overflows reports E-OVERFLOW in `lm test`, like a violated contract; an example cannot expect overflow, because overflow is a bug and not a behavior. The bounds are pinned by runtime fixtures (`tests/spec/run/overflow-*.lm` + `.expect`), not by `semantics.lm` examples.
- Every backend checks explicitly (interpreter after each operation; Go with checked helpers; the future Python backend with an explicit bound), and reports the fault the same way it reports other runtime faults, so the interpreter oracle (ADR-026 Decision 4) can compare outcomes.
Why: it keeps the two promises that matter, that signatures are complete contracts for everything a program does *by design* and that silent wraparound never happens, without adding signature noise to every function that adds. A program that overflows has left the domain its author modeled, which is the same situation as a violated `requires`: stop loudly with a structured diagnostic.
Cost: a program cannot recover from overflow. Revisit: if an experiment needs recovery, add checked stdlib functions returning `Opt` (e.g. `math.add-checked`) rather than a catchable prelude error; if it needs big numbers, add a `Big` type (as ADR-026 already says).
On approval: mark the "Cost:" sentence of ADR-026 Decision 3 as superseded by this ADR; reword ROADMAP M8(b) ("overflow fails `Overflow`" -> "overflow is the runtime fault E-OVERFLOW"); SPEC sections 1, 7, 9, 11 and 13 change when M8(b) is implemented, with the fixtures written first.
